# MyAppFactory V4.0 Batch 2 Security Repair Report

**Date:** 2026-11-01  
**Overall result:** PASS for the requested repairs and executed checks; signed release verification remains NOT RUN.

## Executive summary

The three Batch 2 issues have been repaired without publishing or signing a
production release:

1. Release dashboards now associate evidence with the registered app and reject
   cross-app, out-of-scope, missing, malformed, stale, or integrity-mismatched
   artifact records.
2. Newly generated apps receive the tracked Nova UI root `.gitignore`, covering
   generated build/cache files, local configuration, secrets, signing material,
   IDE files, and OS files.
3. Neither the canonical Nova UI project nor apps generated by the factory use
   the debug key for release builds. Release tasks fail closed unless explicit
   signing environment variables and an existing absolute keystore path are
   provided.

## Issues fixed

### Cross-app release artifact contamination — PASS

`release_readiness_dashboard.py` now:

- Requires a shared artifact index to identify the exact registered project.
- Resolves paths and rejects artifacts outside that app's `build/` or `reports/`
  directories, including paths that resolve outside via symlinks.
- Checks APK/AAB extension and type, project-relative paths when present, exact
  indexed size, and SHA-256 integrity.
- Rejects malformed, missing, stale, or mismatched evidence and exposes
  rejection details as dashboard warnings rather than presenting it as valid
  evidence.
- Preserves app-local legacy index compatibility when the artifact itself is
  contained in that app and current integrity evidence is present.

Regression coverage uses two separate fixture apps and covers both directions
of cross-app contamination, valid project-specific records, shared-index
scoping, outside-project paths, malformed and stale records, and local legacy
compatibility. The artifact and dashboard tests passed.

### Generated root `.gitignore` — PASS

The canonical and starter `.gitignore` files are synchronized and the ignore
file is now among the tracked template files. The app creator copies it as part
of the starter instead of creating a second divergent policy. Tests verify
generated ignore rules and ensure application source/configuration is retained.

### Unsafe release signing — PASS

The canonical Gradle configuration and Android scaffolding produced by
`scripts/create_app.py` no longer select the debug signing configuration for a
release. Both Kotlin DSL and Groovy scaffolds are covered. Release tasks require
all five `MYAPP_RELEASE_*` environment variables, plus an existing absolute
keystore path, or stop with an explicit Gradle error. Debug builds do not need
release credentials.

No signing key was created, checked in, or exposed. A real signed release build
was **NOT RUN** because no approved release key/configuration was supplied.

## Remaining risks and manual setup

- A real release signature was not tested. Before release, obtain a key through
  the organization's approved process and configure the five
  `MYAPP_RELEASE_*` variables in a protected local shell/secret manager or
  protected CI secret store. The instructions are in
  `docs/ANDROID_RELEASE_CHECKLIST.md`.
- The Gradle guard checks that the keystore path is absolute and exists; it
  cannot establish key ownership, strength, validity for the intended
  application, Play App Signing enrollment, or Play policy compliance.
- No production release, AAB upload, Play Console operation, or device test was
  performed.
- The root shared index must associate itself with the registered project.
  App-local compatibility does not permit artifacts outside that app's
  evidence/build directories.
